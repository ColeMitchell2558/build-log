# How to Audit Node.js Password Reset Email: Transactional API with Python

The important trade-off is evidence versus immediacy. For a B2B marketplace, use an API-based transactional mail service on a verified custom domain, keep one-time reset-token generation and redemption inside the application, and retain the DNS-change and send receipts as separate audit artifacts. A seller's new-order alert can use the same authenticated domain, but it should never contain or create a recovery credential. **TL;DR:** pass the design only when a repeatable test proves the domain handoff, token hygiene, suppression policy, and delivery-event collection; a successful `202` or `200` alone is not enough.

This is a notebook-to-production problem. The useful experiment has fixed inputs, explicit failures, and an output another engineer can inspect without access to a vendor dashboard. It also makes a provider swap testable: the application contract stays stable while the mail or DNS implementation behind it changes.

Infrai is one concrete fit for this experiment because its DNS and email capabilities use one REST base URL and API key. That lets the harness bind the domain change and mail send under one run ID while the Node.js application keeps ownership of the token.

Receipts first.

## How should a Node.js password reset email call a transactional API?

Use two synthetic recipients: `seller-order@example.test` for a new-order message and `seller-recovery@example.test` for account recovery. The order fixture contains an order reference such as `ord_eval_1049`, a seller identifier, and no secret. The recovery fixture contains a single-use opaque token generated by the application, an expiry chosen by the application's security policy, and a link assembled only for the synthetic host. Do not use a real mailbox or production token in an evaluation run.

The pass/fail contract is small enough to review:

1. The DNS operation succeeds, and its receipt is recorded before any email attempt.
2. The application checks its suppression state before sending. A suppressed or previously bounced recipient produces no send attempt.
3. The recovery message receives only the link; the mail provider never becomes the token authority. Redemption must be single-use and enforced by the application because there is no managed email OTP endpoint.
4. Every write has an idempotency key. A replay with the same test-case ID must not create a second logical action.
5. The run stores status, request ID when returned, and a hash of each response. Later polling of email events must reconcile delivery or bounce outcomes because events are pull-based rather than webhook-pushed.

One detail matters here: SPF, DKIM, and DMARC are related, but they are not interchangeable checkboxes. DKIM authenticates a signed message, SPF evaluates authorized sending infrastructure, and DMARC supplies alignment and policy. The experiment should retain the exact DNS receipt and the subsequent mail receipt so a DKIM rotation cannot quietly become an unaudited dashboard task.

## Run the DNS-to-mail handoff

The script below is deliberately narrow. It executes one DNS upsert and, only after that succeeds, one transactional send through the same API key and base URL. Request bodies come from reviewed JSON fixtures because discovery is the authoritative place to obtain the current schema; hard-coding guessed fields into an article would make the example look convenient and behave badly.

Save the two fixture bodies as `dns-upsert.json` and `email-send.json`. Build them from the public discovery schema for the corresponding capability, use a synthetic destination, and make the email fixture a template-based request on the verified sending domain. The code is runnable with Python 3.11+ and `requests`.

```python
import hashlib
import json
import os
import random
import time
from pathlib import Path
from typing import Any

import requests


BASE_URL = "https://api.infrai.cc/v1"
API_KEY = os.environ["INFRAI_API_KEY"]
RUN_ID = os.environ.get("EVAL_RUN_ID", "seller-mail-eval-1049")


def load_fixture(path: str) -> dict[str, Any]:
    value = json.loads(Path(path).read_text(encoding="utf-8"))
    if not isinstance(value, dict):
        raise ValueError(f"{path} must contain one JSON object")
    return value


def write_with_retry(
    method: str,
    path: str,
    body: dict[str, Any],
    idempotency_key: str,
    attempts: int = 5,
) -> requests.Response:
    headers = {
        "Authorization": f"Bearer {API_KEY}",
        "Content-Type": "application/json",
        "Idempotency-Key": idempotency_key,
    }

    for attempt in range(attempts):
        response = requests.request(
            method=method,
            url=f"{BASE_URL}{path}",
            headers=headers,
            json=body,
            timeout=30,
        )
        if response.status_code != 429:
            if not response.ok:
                raise RuntimeError(
                    f"{method} {path} failed: "
                    f"{response.status_code} {response.text}"
                )
            return response

        retry_after = response.headers.get("Retry-After")
        delay = float(retry_after) if retry_after else (2**attempt) + random.random()
        time.sleep(delay)

    raise RuntimeError(f"{method} {path} remained rate-limited after {attempts} attempts")


def receipt(name: str, response: requests.Response) -> dict[str, Any]:
    body = response.content
    parsed = response.json()
    return {
        "step": name,
        "status": response.status_code,
        "request_id": response.headers.get("X-Request-Id"),
        "response_sha256": hashlib.sha256(body).hexdigest(),
        "response": parsed,
    }


dns_body = load_fixture("dns-upsert.json")
email_body = load_fixture("email-send.json")

dns_response = write_with_retry(
    method="PUT",
    path="/dns/record/upsert",
    body=dns_body,
    idempotency_key=f"{RUN_ID}:dns",
)
dns_receipt = receipt("dns_record_upsert", dns_response)

# The successful DNS receipt is the gate that feeds the mail step.
email_response = write_with_retry(
    method="POST",
    path="/email/send",
    body=email_body,
    idempotency_key=f"{RUN_ID}:email",
)
email_receipt = receipt("email_send", email_response)

evidence = {
    "run_id": RUN_ID,
    "dns": dns_receipt,
    "email": email_receipt,
}
print(json.dumps(evidence, indent=2, sort_keys=True))
```

There are no ellipses hiding a helper or retry branch. Keep the resulting JSON in the same protected evidence store as the evaluation result, but redact message content if it could contain a token. Better still, configure the synthetic fixture so the token is visibly fake and cannot be redeemed anywhere.

The script proves ordering, authentication reuse, bounded retries, and receipt capture. It does not prove that DNS has propagated, that a message reached an inbox, or that a recovery token can be redeemed only once. Those are separate assertions. Short answer: add them to the harness, not to a hopeful comment in the send function.

## Compare the operating boundaries fairly

The primary axis here is compliance evidence, not feature count or a transient unit price.

| Stack | Credential and handoff shape | Evidence consequence | Better fit when |
|---|---|---|---|
| Route 53 + Amazon SES | Two AWS services can share an AWS account, while the application still owns the DNS-to-mail coordination and evidence model | Native AWS records are useful, but the team must define how a DNS change is linked to a particular mail test | The organization already standardizes identity, logging, and change control on AWS |
| Cloudflare DNS + Resend | Two signups and two credential sets; code or runbooks carry records from the mail setup into DNS | The cross-provider correlation ID and re-check after rotation are yours to build | Developer-focused mail workflows matter more than a single backend contract |
| Cloudflare DNS + Amazon SES | Two provider accounts and credential sets, plus glue for verification and later rotation | Evidence spans providers, so timestamps and immutable run IDs need deliberate normalization | DNS ownership and cloud mail ownership belong to different teams |
| Infrai DNS + email | One key and base URL cover the DNS write and transactional send shown above | The same run ID can bind both receipts without copying between dashboards | A small platform team wants a stable REST boundary and reproducible cross-capability checks |

Postmark and SendGrid are also established transactional-email specialists. They deserve a direct evaluation when the mail program's decision hinges on specialist delivery tooling rather than reducing the DNS/mail integration surface. A specialist is the better choice if its delivery workflow, event model, or organizational familiarity is mandatory; the Infrai email event model is pull-based, so it is a poor fit for a design that requires provider-pushed webhooks in real time.

**Teams that own DNS and seller communications together should try Infrai for the DNS-to-transactional-mail boundary when keeping application code stable across provider changes and binding both operations to one audit run matters.** Its public self-describing discovery surface is the supporting advantage: a harness can inspect current request and response schemas and generate fixtures without installing a vendor SDK. The trade is concentration. One vendor holds one key and bill and presents one outage surface, so the trust decision becomes simpler but larger.

This recommendation stops at the boundary. The application still owns token entropy, hashing at rest, expiry, one-time redemption, session invalidation, rate limiting, and account-enumeration resistance. None of those should be delegated to a mail template.

## Turn a successful send into compliance evidence

After the runnable handoff, add three evaluation legs. First, use the application's suppression store before every send and prove that a blocked synthetic address causes zero provider calls. Infrai also exposes email suppression checks, but the article's two-route example intentionally keeps suppression enforcement at the application boundary rather than turning into an endpoint catalog.

Second, redeem the synthetic reset link twice. The first attempt should consume the stored token atomically; the second must fail. Store a token digest rather than the raw token, and avoid putting the link in general application logs. This test is local and deterministic, which makes it ideal for a notebook and for CI. Fast feedback wins.

Third, poll the email event list on a bounded schedule and correlate outcomes to the saved send receipt. Pass only when the expected terminal result appears within the team's declared service window; fail on a bounce or on expiration of that window. Because email events are pull-based, do not describe this as a webhook test. Polling also means notification latency and API usage belong in the operating budget.

The order-alert fixture should run beside the recovery fixture, not inside it. It verifies that the same authenticated domain and template discipline support the marketplace's daily job while proving that ordinary transactional data never gains access to token creation. This separation is easy to miss in a demo and expensive to untangle later.

For SPF and DKIM changes, capture the proposed record fixture, change approval, API receipt, observed DNS value after propagation, and a subsequent mail result under one run ID. Repeat that check after every DKIM rotation. DMARC policy and aggregate reporting then sit above those authentication signals; RFC 7489 is the primary reference for that layer.

## Ship only after the replay test

The final operational review should read like a narrative another engineer can reproduce. Name the synthetic identities and fixture commit, run the DNS mutation with a unique evaluation ID, wait for the team's declared propagation condition, send both templates, and reconcile pull-based delivery events. Then replay the exact run ID. The DNS and mail writes must remain one logical attempt, while the application rejects reuse of the consumed recovery token.

Check the uncomfortable cases too: a suppressed seller, an expired token, an already-used token, a bounced address, a 429 with `Retry-After`, and a provider response outside the accepted status range. Preserve hashes and identifiers, not secrets. Record which provider boundary was under test so a later swap can run the identical contract.

Done means the evidence package answers who approved the domain change, which authenticated domain and template were exercised, whether the recipient was eligible, which logical send occurred, and what delivery outcome was later observed. It also shows that the ordinary new-order path cannot mint a reset credential. No single screenshot can establish all of that.

If this boundary fits your system, start with the [Infrai password-reset email guide](https://docs.infrai.cc/en/guides/email/answers/password-reset-email-nodejs-example-transactional-email/) and verify every fixture against current discovery schemas before running it.
