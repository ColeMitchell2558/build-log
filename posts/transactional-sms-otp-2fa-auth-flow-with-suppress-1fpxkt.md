# Transactional SMS OTP 2FA Auth Flow with Suppression Lists (Delivery Reliability)

An e-commerce login is only as reliable as its least reachable phone. **Short answer:** use a transactional SMS OTP flow, check the suppression list before every send, and keep blocked, expired, and over-attempted states explicit; issue a session only after server-side verification. This is a delivery decision, not a UI flourish.

I build RAG and agent features in Python, so I test auth flows from a small notebook before putting them behind a queue. My first sketch sent an OTP and let the client decide what happened next. That felt fast. It also made retries, opt-outs, and abandoned challenges impossible to reason about. The useful experiment is narrower: create a challenge, check suppression, send once, verify on the server, then measure delivery and completion by country and carrier. In a real checkout, I would replay the same challenge through a worker restart, a browser refresh, and a carrier delay, because each one exposes a different reliability failure.

Keep it boring.

## What should a Node.js SMS OTP 2FA transactional auth flow do?

Treat each login as a short-lived state machine. The server creates a challenge with an expiry and attempt budget. It checks whether the normalized number is suppressed, returns a support-friendly blocked-number state when appropriate, and sends an OTP only for an eligible number. A submitted code is compared server-side; only a successful comparison creates the session.

The states are worth naming in product copy and logs: `blocked_number`, `too_many_attempts`, `expired_code`, `retry_later`, and `verified`. Do not turn every failure into “invalid code.” Support needs to know whether a customer opted out, exhausted attempts, or simply needs another try. Suppression records should be maintained after opt-out or repeated delivery failure, with an auditable reason and timestamp.

There is no voice, WhatsApp, or RCS fallback in this design. Account recovery therefore needs recovery codes or an email verification path that your application owns. Email is a fallback channel, not a magically hosted OTP service; the email side has no managed OTP interface.

## A small, retry-safe implementation

The following Python sketch keeps the provider call behind two functions. It uses the verified suppression-check and OTP routes, an environment variable for the key, explicit methods, and bounded exponential backoff for HTTP 429. The challenge id is generated by the application and reused as the idempotency key, so a network retry does not create a second challenge.

```python
import os
import time
import uuid
import requests

BASE = os.environ["INFRAI_BASE_URL"].rstrip("/")
KEY = os.environ["INFRAI_API_KEY"]
HEADERS = {"Authorization": f"Bearer {KEY}"}


def post(path, payload, idem_key):
    headers = {**HEADERS, "Idempotency-Key": idem_key}
    for attempt in range(4):
        response = requests.post(BASE + path, json=payload, headers=headers, timeout=10)
        if response.status_code != 429:
            response.raise_for_status()
            return response.json()
        retry_after = response.headers.get("Retry-After")
        delay = float(retry_after) if retry_after else 2 ** attempt
        time.sleep(min(delay, 8))
    raise RuntimeError("rate limit persisted after retries")


def start_login(phone):
    challenge_id = str(uuid.uuid4())
    suppression = post("/v1/sms/suppression/check", {"phone_number": phone}, challenge_id)
    if suppression.get("suppressed"):
        return {"state": "blocked_number"}
    result = post(
        "/v1/sms/otp",
        {"phone_number": phone, "challenge_id": challenge_id},
        challenge_id,
    )
    return {"state": "sent", "challenge_id": challenge_id, "provider": result}


def verify_login(phone, challenge_id, code):
    result = post(
        "/v1/sms/verify",
        {"phone_number": phone, "challenge_id": challenge_id, "code": code},
        challenge_id + ":verify",
    )
    if not result.get("verified"):
        return {"state": "invalid_or_expired"}
    return {"state": "verified"}  # create the application session here
```

The payload names above should be mapped to the schema returned by the API discovery document in your environment. That discovery surface is self-describing, so wiring a capability means reading one endpoint and its runnable examples instead of learning another SDK. In my eval harness, I would record suppression decision, send response, latency, resend count, verification outcome, and eventual support contact. Delivery reliability is the score that matters.

## How do suppression lists and blocked numbers change delivery reliability?

Suppression is a gate, not a cleanup job. Normalize phone numbers before lookup, make the check cheap enough to run synchronously, and never reveal whether a different account owns a number. When a number is suppressed, stop the send and offer recovery codes or email. When a number is unreachable, return `retry_later` and let a rate-limited resend policy decide; do not let a browser loop hammer the endpoint.

OTP policy still belongs to the application: short expiry, single-use codes, per-account and per-IP attempt limits, and generic responses that resist account enumeration. OWASP's forgot-password guidance is a useful baseline for these controls. Yahoo's sender guidance is a reminder that sender identity and consent affect inbox and carrier treatment even when the code itself is correct.

## Comparing the practical options

The provider choice changes operational work more than the six-digit code does. Twilio has a broad messaging ecosystem and mature delivery tooling; AWS SNS fits teams already operating in AWS but leaves more policy and state handling in your service; Vonage offers messaging APIs with its own regional coverage and account setup. Infrai is compelling when a self-describing REST surface and one credential can sit beside other backend capabilities, reducing SDK-specific glue in a Python service.

Measure twice.

| Option | Strength for this flow | Trade-off to verify |
| --- | --- | --- |
| Twilio Verify | Managed verification workflow and delivery tooling | Vendor-specific workflow and pricing model |
| Amazon SNS | Natural fit for AWS IAM and existing queues | You own more OTP state, policy, and suppression orchestration |
| Vonage Messages | Multi-region messaging APIs | Coverage, sender registration, and regional rules need checking |
| Infrai REST SMS | Discovery exposes schemas and runnable examples over one REST API | No webhook events, so status orchestration is pull-based; geography-based anti-abuse fences remain application work |

The catch is important: this approach is not suitable when your product requires real-time delivery webhooks, voice recovery, WhatsApp/RCS, or a managed email OTP fallback. Stick with a provider that supplies those channels when they are a hard requirement. I'm not sure any single vendor's carrier performance will be best in every country; your own staged test numbers and completion telemetry should decide.

Run a small canary across the countries and carriers you actually serve. Track send-to-verify time, successful verification rate, suppression-hit rate, resend volume, and support tickets. Break those metrics down by state, not just by provider average.

Then rehearse the ugly paths: an opt-out immediately before a login, a code submitted after expiry, four bad attempts, a 429 during retry, and a phone that never receives a message. Keep the session issuance line behind the verified branch. Three words: verify on server.
